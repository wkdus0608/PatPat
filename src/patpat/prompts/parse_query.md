# PatPat 관찰 분류 프롬프트 — parse_query.md (강의 3 산출물, 초안)

| 항목 | 값 |
|---|---|
| prompt_version | 1 |
| 짝이 되는 스키마 | `src/patpat/schemas/observation.schema.json` |
| 읽는 코드 | 미구현. 관찰 분류 코드가 아래 `prompt:start`와 `prompt:end` 마커 사이만 읽어 system 프롬프트로 보낸다 |
| 쓰이는 곳 | `POST /observations`의 외부 AI 분류 단계 (SPEC 3·5절) |
| 누가 쓰는가 | 👤 사람이 확정한다. 이 초안은 AI가 작성했으며 팀 검토 전이다 |

## 이 파일은 어떻게 쓰이나

- **마커 안은 런타임에 외부 AI로 전송되는 프롬프트**이고, 마커 밖은 팀이 읽는 문서다. 코드는 마커 밖을 읽지 않는다.
- **입력은 로컬 가명 처리를 마친 텍스트뿐이다.** 원본 음성, 실명, 실명↔가명 매핑표는 이 프롬프트에도 사용자 메시지에도 들어가지 않는다. 가명 처리가 실패하면 이 프롬프트를 호출하지 않는다 (SPEC 4절, AC10).
- **사용자 메시지 형식**: 코드가 아래 두 줄을 만들어 보낸다. 요청 아동 목록은 모델이 알 수 없는 기준 정보라서 코드가 채운다.
  ```
  요청 아동: C01, C02, C03
  메모: <가명 처리된 메모>
  ```
- **`observation_id`는 모델이 만들지 않는다.** 코드가 스키마 검증을 통과한 `observations` 배열에 원문 등장 순서대로 부여한다 (AGENTS.md 5절). 관찰의 발생 날짜도 모델이 추측하지 않고 코드가 저장 시 함께 남긴다 (SPEC 5절).
- **버전 규칙**: 마커 안이 바뀌면 `prompt_version`을 올리고 변경 이력에 한 줄 적는다. 측정 기록에는 모델 ID, `prompt_version`, 스키마 커밋을 함께 적는다.

## 시스템 프롬프트 (모델에 전송되는 부분)

<!-- prompt:start -->
너는 PatPat의 관찰 분류기다. 어린이집 교사가 남긴 메모를 아동별 관찰로 나누어 주어진 JSON 스키마에 정확히 맞는 객체 하나를 출력한다. 메모의 아동 이름은 이미 가명 코드(C01, C02 …)로 바뀌어 있다.

규칙:
- 메모에 없는 사실을 만들지 않는다. 행동·발화·감정·부상을 추측하거나 덧붙이지 않는다.
- text에는 그 관찰의 사실을 담은 메모 부분을 그대로 옮긴다. 요약하거나 다른 말로 바꾸지 않는다.
- child_ids에는 '요청 아동'에 있는 코드만 쓴다. 메모에서 그 아동의 일이라고 드러난 경우에만 연결한다.
- 한 아동의 사실을 다른 아동의 관찰에 넣지 않는다. 서로 다른 아동의 행동은 서로 다른 관찰로 나눈다.
- 여러 아동이 함께 겪은 한 사건은 관찰 하나로 두고 관련 아동 코드를 모두 넣는다.
- '다 같이', '반 전체'처럼 요청 아동 전체를 가리키는 말이면 요청 아동의 코드를 모두 넣는다.
- 누구의 일인지 메모에서 알 수 없는 문장은 아동을 추측해 연결하지 않고 관찰로 만들지 않는다.
- activity에는 메모에 나온 활동명을 그대로 쓴다. 메모에 활동이 없으면 null로 둔다.
- 관찰은 메모에 나온 순서대로 적는다. 연결할 관찰이 하나도 없으면 observations를 빈 배열로 둔다.
- 출력은 JSON 객체 하나만 쓴다. 설명, 코드 펜스, 주석을 붙이지 않는다.

예시 1
입력:
요청 아동: C01, C02, C03
메모: 모래놀이. 다 같이 모래성 만들기. C01은 삽으로 물길 팜. C03이 C02 모래성 밟아서 C02 울음, 서로 사과함.
출력: {"observations":[{"child_ids":["C01","C02","C03"],"activity":"모래놀이","text":"다 같이 모래성 만들기"},{"child_ids":["C01"],"activity":"모래놀이","text":"C01은 삽으로 물길 팜"},{"child_ids":["C02","C03"],"activity":"모래놀이","text":"C03이 C02 모래성 밟아서 C02 울음, 서로 사과함"}]}

예시 2
입력:
요청 아동: C01, C02
메모: 오늘 좀 피곤해 보였음. 낮잠 늦게 잠.
출력: {"observations":[]}
<!-- prompt:end -->

## 필드 → 함수 인자 (하드/소프트)

코드가 아직 없으므로 함수 이름은 예정이다. 오른쪽 열에 답하지 못하는 필드는 두지 않는다. **하드**는 위반 시 그 관찰을 저장하지 않고 교사 확인으로 넘기는 것, **소프트**는 비어 있어도 진행하는 것이다.

| 필드 | 어느 함수의 어느 인자로 가는가 | 하드/소프트 |
|---|---|---|
| `child_ids` | 후처리 `check_child_ids(observation, request_child_ids)`(요청 아동의 부분집합인지) → 저장 → `POST /drafts`에서 아동별 근거 선택과 `missing_evidence` 판정 (AC1, AC3, AC4) | **하드** |
| `text` | 후처리 `check_text_in_memo(observation, memo)`(메모에 실제로 있는 부분인지) → 저장 → 초안 문장의 근거 대조 (AC1, AC2, AC6) | **하드** |
| `activity` | `POST /drafts`에서 같은 활동의 관찰을 묶어 `common_text`를 만들 때의 묶음 기준 | 소프트. null이면 활동 없이 진행 |
| `observation_id` | 모델 출력에 없음. 코드가 부여해 `individual_sentences[].observation_ids`로 쓰인다 | — |

**온톨로지 `Observation` 속성 중 이 스키마에 넣지 않은 것**과 이유. SPEC 5절 API 필드에 없고 v1에서 어느 함수도 쓰지 않는다. 온톨로지 속성을 API에 임의로 추가하지 않는다(AGENTS.md 2절).

| 속성 | 넣지 않은 이유 |
|---|---|
| `observation_type`, `individual_detail` | 조사 분류다. v1 초안 생성은 원문 `text`만으로 판정한다 |
| `scope` | `child_ids`의 개수·범위로 공통/개별/공동을 표현한다. 주체 미확정(`unresolved`)은 아래 v1의 한계 참조 |
| `content_kind` | 관찰일지의 기관별 서식 항목이며 현재 필수 항목이 아니다 (온톨로지 note) |
| `needs_confirmation` | 담을 API 필드가 없다. 아래 v1의 한계 참조 |

## 실패 모드 점검표

| # | 실패 모드 | 점검 입력 | 어디서 잡히나 | 그다음 |
|---|---|---|---|---|
| 1 | (정상) | 요청 C01·C02 / "블록 놀이. C01 높은 탑 쌓음. C02 탑 옆에 자동차 길 만듦." | 스키마 통과, `child_ids`·`text` 후처리 통과 | 코드가 `observation_id`를 부여해 저장 |
| 2 | 정보 부족 | 요청 C01·C02 / "오늘 좀 피곤해 보였음." | 스키마 통과(`observations: []`). 저장 단계에서 연결된 관찰 0건 확인 | 모델을 다시 부르지 않고 교사에게 누구의 일인지 확인 요청 |
| 3 | 모호한 주체 | 요청 C01·C02 / "C01이랑 놀다가 넘어져 무릎 긁힘." | 넘어진 아동이 C01인지 다른 아동인지 메모로 알 수 없음. 모델이 추측해 연결하면 스키마로는 못 잡는다 | 교사 검토 화면에서 원문과 관찰 목록을 나란히 보여 준다. 부상은 초안에서 `special_notes`로 분리(AC7) |
| 4 | 범위 위반 | 출력에 `"child_ids": []` 또는 `"text": ""` | 스키마 `minItems: 1`, `minLength: 1` 위반 → 검증 실패 | 오류 메시지를 붙여 1회 재요청 |
| 5 | 지원 밖 코드 | 요청 C01·C02 / "C01, C05랑 공놀이." | 출력에 `C05`가 있으면 `check_child_ids`에서 불일치 | 그 관찰을 저장하지 않고 교사 확인 요청. 추측해 다른 코드로 바꾸지 않는다 |
| 6 | 사실 추가·바꿔 쓰기 | 출력 `text`가 "C01이 즐겁게 탑을 쌓음"(메모에 '즐겁게' 없음) | `check_text_in_memo`에서 메모에 없는 문자열로 걸림 | 오류 메시지를 붙여 1회 재요청 |
| 7 | 스키마에 없는 키 | 출력에 `"emotion": …` 또는 `"observation_id": …` | `additionalProperties: false` → 검증 실패 | 오류 메시지를 붙여 1회 재요청 |
| 8 | JSON 아님 또는 절단 | 응답이 `max_tokens`로 끊김, 파싱 실패 | 응답 상태 확인과 JSON 파싱 | 1회 재요청 |
| 9 | 실명 유입 | 가명 처리 실패로 메모에 이름이 남은 경우 | 이 프롬프트 호출 전, 로컬 가명 처리 단계 (AC10, GC-16) | 외부 호출 0건. 교사 확인 요청 |

- **재시도 정책**: 재요청은 형식·원문 불일치 오류(4, 6, 7, 8)에만 1회 한다. 정보 부족과 주체 문제(2, 3, 5)는 다시 불러도 없는 정보가 생기지 않으므로 재요청하지 않고 교사에게 확인한다. 2회 연속 실패하면 분류를 포기하고 교사에게 아동별 입력을 요청한다. 추측해서 진행하지 않는다.
- **점검 결과**: 위 점검 입력은 아직 실행하지 않았다. 실행 도구와 모델이 정해지면 결과를 이 절에 기록한다.
- **v1의 한계**: 주체를 알 수 없어 관찰로 만들지 않은 문장은 출력에 남지 않는다. 그래서 2번처럼 전부 빠지면 알 수 있지만, 메모 일부만 빠진 경우는 모델 출력만으로 알 수 없다. 이런 문장을 담을 필드(온톨로지 `needs_confirmation`)를 API에 넣을지는 SPEC 변경이 필요한 팀 결정이다.

## 변경 이력

- v1 (2026-10-03): 최초 초안. SPEC 5절 `POST /observations` 출력 필드와 골든 케이스 GC-04~06·GC-12의 관찰 형태에 맞춤. 예시는 골든 케이스 입력과 겹치지 않게 새로 만들었다.
