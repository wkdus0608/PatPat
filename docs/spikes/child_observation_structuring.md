# 스파이크 — 아동별 관찰 구조화

가설 ID: SP-01 / 상태: 실험 계획, 미실행 / 수정일: 2026-09-30
연결: [SPEC](../SPEC.md) 5절 관찰 입력·AC2·AC3, [골든 케이스](../golden_cases.yaml) GC-12, [온톨로지](../ontology.yaml) Observation

현재 SPEC의 필드에 맞춰 기존 계획을 간소화했다. 시간·비용·합격선은 기존 계획의 값을 유지한 초안이며, 팀이 실행 전에 확정한다. 아래 결과는 아직 측정하지 않았다.

## 1. 가장 위험한 가정

**짧은 메모에 여러 아동의 이야기가 섞여 있어도, 입력에 있는 사실을 빠뜨리거나 추가하지 않고 해당 아동의 관찰로 나눌 수 있다.**

- 실패 영향: 첫 단계에서 아동을 잘못 연결하면 이후 알림장·일지도 다른 아이의 사실로 작성된다. 근거 번호가 있어도 기록을 신뢰할 수 없다. (로그 2, 4, 7, 9)
- 근거 부족: 조사에서는 아이별 행동을 되찾고 나눠 쓰는 부담을 확인했지만, 모델이 짧은 메모를 얼마나 정확히 나누는지는 측정하지 않았다.
- 대체 비용: 실패하면 교사가 처음부터 메모를 아이별로 나눠 입력해야 하므로 추가 작업이 생긴다.
- 우선 선정 이유: 음성 전사는 텍스트 입력으로 먼저 대체할 수 있다. 초안 작성보다 앞선 아동별 관찰 연결을 먼저 확인한다.

검증 대상은 SPEC 5절의 텍스트 관찰 입력이다. 출력은 `observations` 배열이며 관찰마다 `observation_id`, `child_ids`, `activity`, `text`를 사용한다. 이번 평가는 활동명과 아동 코드가 명시된 메모에 한정하며, 음성 인식·문장 생성·사용자 시간 단축은 측정하지 않는다.

개인정보 처리의 전제는 **로컬 AI 전사·가명 처리 → 외부 AI API 분류·기록 생성 → 로컬 실명 복원**이다. 이번 스파이크는 그중 가명 텍스트의 아동별 분류만 검증한다. 외부 모델에는 가명 메모만 보내고 원본 음성·실명·매핑표를 보내지 않는다. 로컬 처리·복원 및 AC10 전체의 통과 여부는 이 실험으로 판단하지 않는다. (팀 회의 결정, SPEC 4절)

## 2. 시간 제한

준비·라벨 작성·실행·대조·기록을 합해 최대 6시간, API 비용 최대 10,000원으로 잡는다.

6시간 경과, 비용 상한 도달, 평가 30건 완료 중 먼저 오는 시점에 멈춘다. 준비 시간이 길어져 평가를 마치지 못해도 상한을 늘리지 않고 판단 보류로 기록한다.

## 3. 성공 조건 (실험 전에 확정)

**평가용 메모 30건 중 27건 이상(90%)이 사람의 정답과 일치하고, 아동 혼동·없는 사실 추가가 0건이어야 한다.**

- 평가 단위: 메모 1건. 한 아동의 메모, 여러 아동의 서로 다른 행동이 섞인 메모, 공통 활동·공동 사건 메모를 포함한다. 가명 코드와 가상 관찰을 사용하며 출처와 데이터 버전을 기록한다.
- 데이터 분리: 프롬프트를 준비할 5건과 평가할 30건을 따로 만든다. 골든 케이스는 동작 확인에만 쓰고 평가 30건에 그대로 넣지 않는다.
- 건별 판정: 메모의 모든 관찰이 정답과 같은 아동 집합·활동·사실을 가져야 통과한다. 일부만 맞으면 해당 메모는 실패다. 관찰 배열과 아동 집합의 순서는 채점에 영향을 주지 않으며, 뜻을 보존한 표현 차이는 허용한다.
- 검사 방법: 필드·ID·아동 집합은 자동으로 대조한다. 활동과 관찰 문장의 의미는 팀원 2명이 정답·원문과 비교하고, 판단이 갈리면 합의해 기록한다. 번호 형식이 맞는 것만으로 사실성이 통과하지 않는다.
- 치명 오류: 다른 아동에게 사실을 옮기거나 원문에 없는 행동·발화·감정·부상을 추가하면 1건이라도 채택하지 않는다.
- 집계: 호출 실패도 실패 건으로 센다. 평가를 중단해 30건을 끝내지 못하면 판단 보류이며, 완료한 건만으로 전체 합격을 선언하지 않는다.

이 기준은 이번 구조화 방식의 채택 판단용이다. 제품 전체의 AC 통과나 현장 성능을 뜻하지 않는다. 팀은 실행 전에 기준을 확정하고 결과를 본 뒤 낮추지 않는다.

## 4. 방법

1. **정답 만들기:** 팀원 2명이 평가 메모 30건을 서로의 답을 보지 않고 각각 아동·활동·사실로 나눈다. 다른 답은 원문을 함께 읽어 합의한다. 사람 사이의 라벨 불일치 건수를 기록한다.
2. **모델 출력 만들기:** 외부 AI 모델 1개와 현재 SPEC 필드에 맞는 구조화 출력 형식을 사용한다. 준비용 5건으로 연결을 확인하고, 모델·프롬프트·설정·버전을 고정한 뒤 평가 메모마다 1회 실행한다. 평가 정답을 모델에 주거나 평가 도중 프롬프트를 수정하지 않는다.
3. **대조와 기록:** 자동 검사와 의미 판정으로 메모별 통과·실패 및 이유를 기록한다. 일치율과 치명 오류를 합격선과 비교하고, 실제 출력과 오류 예를 남긴다. UI 개발이나 프롬프트 최적화는 이 실험에 포함하지 않는다.

실행할 때 아래 항목을 실제 값으로 채운다.

| 실행 정보 | 현재 상태 |
|---|---|
| 준비·평가 데이터 파일과 버전 | 미준비 |
| 팀원별 라벨과 합의 정답 파일 | 미작성 |
| 시간·비용·판정 기준의 팀 확정 | 미확정 |
| 모델·버전·프롬프트·설정 | 미선정 |
| 실행 코드·명령·실행 일시 | 미실행 |

## 5. 결과

| 항목 | 결과 |
|---|---|
| 평가 완료 건수 | 미측정 / 목표 30건 |
| 일치 건수·일치율 | 미측정 / 기준 27건 이상(90%) |
| 치명 오류 건수 | 미측정 / 기준 0건 |
| 사람 간 라벨 불일치 건수 | 미측정 |
| 실제 소요 시간·API 비용 | 미측정 |
| 실험 판정 | 미실행 |
| 실제 모델 출력·합의 정답·채점 파일 위치 | 미생성 |

실행 후 불일치는 아동 혼동, 사실 추가, 사실 누락, 활동 연결 오류, 형식·호출 오류로 나눠 건수와 실제 예를 적는다. 한 메모에 여러 오류가 있으면 유형별 중복 집계임을 표시한다. 사람 간 라벨 불일치와 모델 오류는 별도로 센다.

## 6. 판단과 재도전 조건

현재 판단: **판단 보류 — 평가 데이터·사람 정답·실제 모델 출력이 아직 없다.** 이번 문서 작성으로 자동 구조화의 타당성이 확인된 것은 아니다. 실험 결과에 따른 SPEC·온톨로지 변경도 아직 없다.

- **기준 충족:** 명시된 아동·활동이 있는 텍스트의 구조화 방식을 다음 구현에 채택할 근거로 삼는다. SPEC 5절 관찰 입력에 실험 근거를 연결한다.
- **기준 미달 또는 치명 오류 발생:** 오류 원인을 보고 자동 분리 방식을 유지할지, 교사가 아동별로 나눠 입력하는 방식으로 바꿀지 팀이 판단한다. 결정한 입력 방식은 SPEC 3~5절과 골든 케이스 GC-12에 함께 반영한다. 개념 정의가 바뀔 때만 온톨로지도 수정한다.
- **평가 미완료:** 성능 실패로 단정하지 않고 준비가 부족했던 항목과 완료 건수를 적어 판단 보류한다.

재도전은 오류 원인을 보완할 입력 규칙이나 실행 조건을 마련했을 때 진행한다. 바꾼 조건과 새로운 평가 데이터를 기록하고, 같은 파일의 이 절 아래에 회차를 덧붙인다.
