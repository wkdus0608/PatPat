# 스파이크 — 아동별 관찰 구조화

가설 ID: SP-01
상태: 설계 초안, 미실행 / 작성일: 2026-09-28
연결: [SPEC](../SPEC.md) AC3·AC4·AC11, [온톨로지](../ontology.yaml) Observation
이 기록은 실행 계획이다. 평가 데이터·사람 라벨·모델·합격선은 실행 전에 팀이 확정하며, 아래 수치는 실측 결과가 아니다.

## 1. 가장 위험한 가정

**짧고 여러 아동의 이야기가 섞인 메모를, 없는 사실이나 아동 혼동 없이 아동·활동별 관찰로 구조화하고 모호한 주체는 보류할 수 있다.**

- 실패 영향: 잘못 연결한 관찰로 초안을 만들면 근거 번호가 있어도 다른 아동의 기록이 된다. 이후 초안 생성·사실 검토의 출발점이 무너진다(로그 2, 4, 7, 9).
- 근거 부족: 인터뷰는 기억·메모·개별화의 부담을 보여 주지만, 자유 메모의 실제 모델 파싱 품질은 측정하지 않았다.
- 대체 비용: 교사가 모든 메모를 처음부터 아동별로 나누거나 직접 라벨해야 한다. 이 추가 작업이 시간 절감 효과를 없앨 수 있다.
- 다른 후보: 음성 전사는 확인된 텍스트로 우선 대체할 수 있고, 사진 분석은 비범위다. 초안 사실성은 다음 검증 대상이며, 첫 단계의 아동 연결을 먼저 확인해야 한다.

검증 범위는 `POST /observations`의 텍스트 구조화다. 음성 인식, 초안 작성, UI, 사용자 시간 단축은 이 실험의 결과로 판정하지 않는다.

## 2. 시간 제한

제안: 준비·독립 라벨·합의·모델 실행·대조·기록을 합해 최대 6시간, API 비용 상한 10,000원. 두 한도는 실행 전에 팀이 확정한다.

종료 조건은 시간 또는 비용 상한 도달, 평가 30건 완료 중 먼저 오는 시점이다. 데이터·실행 환경이 준비되지 않거나 평가를 마치지 못하면 판단 보류로 남긴다. 준비에 걸린 시간도 기록하고 상한을 임의로 연장하지 않는다.

## 3. 성공 조건 (실험 전에 확정)

### 평가 단위와 데이터

평가 단위는 메모 1건이다. 프롬프트 작성용 5건과 평가용 30건을 분리한다. 기존 golden_cases는 개발·판정 규칙 확인에만 쓰고, 그대로 최종 평가 세트에 넣지 않는다.

제안한 평가 30건 구성:

| 주된 상황 | 건수 |
|---|---:|
| 한 아동의 명확한 관찰 | 8 |
| 공통 활동만 있는 메모 | 6 |
| 여러 아동의 서로 다른 행동이 섞인 메모 | 8 |
| 공동 사건·민감 상황 | 4 |
| 주체가 모호한 메모 | 4 |
| 합계 | 30 |

교사가 입력한 배움·지원·미래 계획의 구분 사례는 위 범주에 일부 포함한다. 수집한 메모 또는 팀이 만든 가명 가상 메모의 출처를 건별로 적는다. 가상 메모의 결과를 현장 입력 성능으로 일반화하지 않는다.

### 건별 판정 규칙

팀원 2명이 원문을 보고 각각 다음 정답을 붙인 뒤 불일치를 합의한다.

- 각 관찰의 아동 집합과 scope
- activity(확인 불가면 null), content_kind
- 원문에 근거한 핵심 사실과 정확한 발췌
- 주체 불명확이면 child_ids: [], scope: unresolved, needs_confirmation: true

메모 1건의 모든 관찰이 정답의 아동 집합·scope·content_kind·핵심 사실·확인 필요 여부와 일치해야 통과다. activity는 같은 뜻을 허용하고, 원문에 없으면 추가하지 않는다. evidence_text는 정확한 원문 부분이며 그 의미도 관찰을 뒷받침해야 한다. JSON 배열 순서는 채점에서 무관하지만 출력 순서는 SPEC대로 유지한다.

아동 혼동, 없는 사실 추가, 모호한 주체를 특정 아동으로 확정, 공동 사건을 잘못된 아동에게 배분한 것은 치명 오류다. 키워드 일치나 유효한 JSON만으로 통과하지 않는다.

### 합격선 제안

- 30건 중 27건 이상 완전 일치(90% 이상).
- 치명 오류 0건.
- 미완료 평가를 분모에서 빼서 점수를 올리지 않는다.

이는 이번 텍스트 구조화 방식의 다음 개발 단계 채택 여부를 보는 제안이다. 제품 전체의 AC 통과나 무오류 보증이 아니다. 팀이 수치와 판정 규칙을 실행 전에 확정하고 고정하며, 결과를 보고 낮추지 않는다.

## 4. 방법

1. 정답 만들기: 개발용과 평가용 메모를 분리하고 버전·출처를 기록한다. 평가 30건은 팀원 2명이 서로의 라벨을 보지 않고 판정한 후 합의한다. 사람 사이의 불일치 건수도 별도로 기록한다. AI가 만든 정답을 사람 정답으로 표시하지 않는다.
2. 최소 실행 준비: 모델 1개를 선정하고 SPEC의 Observation 계약에 맞는 구조화 출력 스키마·프롬프트·설정·모델 버전·실행 명령을 고정한다. API 키는 저장소에 넣지 않는다. 개발용 5건으로 연결만 확인하고 평가 데이터를 보며 프롬프트를 수정하지 않는다.
3. 모델 출력 만들기: 평가 메모마다 1회 실행해 원본 응답과 지연 시간·비용·실패를 모두 저장한다. 실패한 요청도 평가 건수에 포함한다. 정답 라벨은 모델에 전달하지 않는다.
4. 대조: 스키마·ID·원문 발췌를 기계적으로 검사하고, 핵심 사실·아동 귀속·모호성은 두 사람의 정답과 대조한다. 미일치 이유와 실제 예를 건별로 남긴다. 자동으로 고친 결과를 원래 모델 출력의 성공으로 세지 않는다.
5. 정리: 합격선과 비교하고, 구조화 자동화 채택·교사 확인 보강·수동 아동별 입력 전환·판단 보류 중 하나를 근거와 함께 선택한다. 프롬프트 최적화나 UI 개발은 이 실험에서 진행하지 않는다.

## 5. 결과

| 항목 | 결과 |
|---|---|
| 평가 완료 건수 | 미측정 |
| 완전 일치 건수·비율 | 미측정 |
| 치명 오류 건수 | 미측정 |
| 사람 간 라벨 불일치 건수 | 미측정 |
| 오류 유형·실제 출력 예 | 미수집 |
| 응답 시간·비용 | 미측정 |
| 실험 판정 | 미실행 |

실제 모델 출력과 합의 라벨이 없는 상태다. 예시 결과나 임의 수치를 결과 칸에 넣지 않는다.

## 6. 판단과 재도전 조건

현재 판단: **보류 — 실험이 아직 실행되지 않았다.** SPEC v1 확정도 보류한다.

| 실제 결과가 나오면 | SPEC에 반영할 판단 |
|---|---|
| 일치 기준 충족, 치명 오류 0건 | 텍스트 구조화 방식을 다음 구현 후보로 채택. 교사 정정·모호성 보류는 유지하고 초안 사실성·음성 품질을 별도로 검증. |
| 아동 혼동·주체 추측 발생 | 자동 아동 연결을 채택하지 않고 교사가 아동을 지정·확인하는 구조로 변경. API와 AC11·golden_cases를 함께 수정. |
| 누락·분류 오류로 일치율 미달 | 입력 길이·형식·검토 방식 등 오류 원인을 보고 방식 변경 또는 재실험을 결정. |
| 평가·라벨·환경 준비 미완료 | 기술 실패로 단정하지 않고 판단 보류. 필요한 준비물과 남은 평가를 기록. |

재도전은 이 문서의 아래에 회차를 추가한다. 바꾼 입력 규칙·스키마·프롬프트·모델을 기록하고, 기존 평가 메모에 맞춰 개선했다면 새로운 평가 세트를 준비한다. 개념 경계가 바뀌면 ontology.yaml, 구현 방식·범위가 바뀌면 SPEC과 golden_cases를 먼저 갱신한다.

기술 결과와 별도로, 교사가 보육을 방해하지 않는 시점에 메모를 남길 수 있는지와 입력·검토를 합친 전체 시간이 줄어드는지는 사용자 평가로 확인한다.
